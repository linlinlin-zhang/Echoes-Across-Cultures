# `merge_metadata_dedup.py` 代码说明

对应源码：[E:/Desktop/Echo/dcas/scripts/merge_metadata_dedup.py](E:/Desktop/Echo/dcas/scripts/merge_metadata_dedup.py)

## 1. 这个文件在数据链路里负责什么
这个脚本负责把多份已经导入好的 `metadata.csv` 合并成一张总表，并按 `track_id` 去重。

它在整条链路中的位置通常是：

- 各个来源或各个文化域已经各自生成了 `metadata.csv`
- 现在需要把它们拼成一张总表
- 同时要把 `audio_path` 统一解析成稳定路径

所以它是“多来源汇总层”的核心脚本。

## 2. 整体执行流程
主流程在 `merge_metadata_dedup(...)` 中：

1. 读取所有输入 CSV
2. 检查每份表是否至少含有 `track_id / culture / audio_path`
3. 统计所有表的字段并构建总字段集
4. 遍历每一行，按 `track_id` 去重
5. 把 `audio_path` 转成绝对路径
6. 合并出总表并写到目标位置
7. 生成 `*.merge_report.json`

## 3. 辅助函数流程说明
这个文件的辅助函数很少，基本就是在给主流程做输入准备：

1. `_read_csv(...)`
   - 逐个读入每份 metadata 和它们各自的字段名
   - 让主流程后面能够同时做：
     - 必需字段检查
     - 字段并集构建
     - 逐行去重与合并

所以这里的关系很简单：

- `_read_csv(...)` 负责把每份来源表完整读进来
- `merge_metadata_dedup(...)` 再基于这些读入结果做 schema 检查、去重、路径标准化和合并

## 4. 辅助函数说明
### `_read_csv(path)`
作用：

- 读取 CSV
- 返回：
  - 行列表
  - 字段名列表

这个函数简单，但它把“读取数据”和“读取 schema”同时统一封装了。

## 5. 核心函数 `merge_metadata_dedup(inputs, out_csv)`
### 4.1 参数解释
`inputs`

- 多个输入 `metadata.csv`
- 顺序是有意义的，因为去重时“先出现的记录优先保留”

`out_csv`

- 合并后的输出 CSV 路径

### 4.2 为什么它先检查必需字段
每份输入表都必须至少有：

- `track_id`
- `culture`
- `audio_path`

原因很简单：

- 没有 `track_id`，无法做去重和对齐
- 没有 `culture`，无法做后续文化分析
- 没有 `audio_path`，样本就不是可消费的音频资产

### 4.3 去重逻辑是怎么做的
这个脚本目前采用的是工程层面的简单去重：

- 维护一个 `seen_track_ids`
- 新行的 `track_id` 如果已出现，则跳过

这意味着它解决的是：

- 同一条记录在多份 metadata 中重复出现

但它不解决：

- 内容相似但 `track_id` 不同的近重复样本

这个 distinction 在面试里很值得强调。

### 4.4 为什么要把 `audio_path` 解析成绝对路径
不同输入 CSV 往往来自不同目录。

如果继续保留相对路径：

- 合并后的大表会很难直接使用
- 后续脚本在不同工作目录下运行时容易找不到音频

因此这个脚本会把每一行的 `audio_path` 相对于该行所属 CSV 的目录解析成绝对路径，再写到总表里。

这是一个很典型但非常关键的工程细节。

### 4.5 输出字段顺序为什么要特殊处理
脚本定义了一个 `preferred` 字段顺序：

- `track_id`
- `culture`
- `audio_path`
- `source_dataset`
- `source_split`
- `source_index`
- `label`
- `affect_label`

其余字段再追加到后面。

这样做的好处是：

- 主字段永远放前面，便于人工检查
- 兼容不同来源带来的额外列
- 不会丢失异构元数据

## 6. 输出报告说明
`*.merge_report.json` 会记录：

- 输出路径
- 最终行数
- 输入源数量
- 每个输入源合并前后保留了多少条
- 文化分布
- 跳过的重复数量

这个报告很适合用于回答：

- 我们到底合了几份表
- 哪些来源贡献最多
- 去重有没有实际发生

## 7. 这个脚本在 V4 主线里的意义
在 V4 主线里，很多数据并不是重新从互联网抓，而是从 V3 已经准备好的多来源 metadata 重新汇总。

在这种场景下，`merge_metadata_dedup.py` 的作用就非常核心：

- 它是从“多份来源级 metadata”迈向“一张主表”的第一步
- 后面的 `harmonize_v4_metadata.py`、`audit_dataset_v4.py` 都依赖它的输出

## 8. 设计优点
### 优点 1：实现简单、透明、可追溯
去重规则非常明确，不是黑箱。

### 优点 2：字段兼容性好
不同来源的额外字段不会被直接丢弃。

### 优点 3：路径处理正确
把相对路径统一成绝对路径，是后续整条链路稳定运行的重要前提。

## 9. 局限与注意点
### 局限 1：只按 `track_id` 去重
不会做声学相似度去重，也不会做标题/艺术家级近似去重。

### 局限 2：先到先得
如果同一个 `track_id` 在不同表里冲突，后出现的那条会被跳过，没有更复杂的保留策略。

### 局限 3：不会做字段标准化
这个脚本只负责合并，不负责 schema 清洗和标签统一。

## 10. 面试时怎么讲
可以这样说：

“`merge_metadata_dedup.py` 是多来源汇总阶段的关键脚本。它把多份 `metadata.csv` 合成一张主表，先检查最基础的三列是否存在，再按 `track_id` 做工程级去重，并把每条记录的 `audio_path` 统一解析成绝对路径。这样后续的 schema 标准化、标签统一和数据审计才能在一张稳定主表上继续进行。”

## 11. 建议重点看哪里
优先看：

1. 必需字段检查
2. `seen_track_ids` 去重逻辑
3. `audio_path` 转绝对路径
4. `preferred + extra` 的字段排序策略

理解这几个点，你就能把“合并去重层”的作用讲清楚。
