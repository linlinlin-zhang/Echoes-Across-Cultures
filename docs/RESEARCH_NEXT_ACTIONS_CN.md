# DCAS 项目研究现状与下一步行动建议

更新时间：2026-03-10

## 1. 这份文档是干什么的

这份文档用于回答一个非常具体的问题：

> 现在这个项目的研究部分已经做到哪一步了？接下来最该做什么？为什么要这么做？应该按什么顺序做？

目标不是再重复一遍代码目录，而是把当前研究状态、证据边界、优先级判断、执行顺序和背后的原因全部讲清楚，便于后续决策、分工和论文写作。

---

## 2. 一句话结论

当前项目已经完成了一个**可复现的研究原型闭环**，并且已经推进到 **Phase 4 的模型迭代与统一评测阶段**。  
但是，它还没有进入“大规模真实跨文化基准已经充分验证”的状态。

因此，**现在最重要的工作不是继续改前端，也不是立刻做大规模 backbone 微调，而是先补足真实数据与真实专家反馈这一块证据链**。

更准确地说，当前最该做的是：

1. 建一个更干净、可复现、可扩展的真实跨文化数据集 v1。
2. 设计并执行一套真实专家标注流程。
3. 把真实标注通过 PAL / ontology / pairwise constraints 回灌到训练中。
4. 在现有统一评测框架下，验证这些真实标注是否带来稳定收益。
5. 只有在这一步仍然卡住时，再考虑更重的模型升级，例如 backbone 微调或更复杂的生成建模。

---

## 3. 当前项目已经完成了什么

### 3.1 核心研究链路已经打通

从当前仓库状态来看，以下研究能力都已经不是纸面设计，而是已经有代码、脚本、实验输出和报告支撑：

- 三因子解纠缠建模：`zc / zs / za`
- 领域对抗去文化化
- 对比学习约束
- OT / Sinkhorn 跨文化推荐
- PAL 不确定性选样
- Pairwise constraints 回灌训练
- 动态本体（ontology）管理与约束导出
- 统一评测脚本（推荐 + 解纠缠 + 显著性检验）
- CultureMERT embedding 级数据构建流程
- embedding 级风格迁移与波形级 baseline

这意味着项目已经不是“想法阶段”，而是一个**能跑、能评、能迭代的 research prototype**。

### 3.2 研究已经从 toy 数据推进到了真实数据原型

当前仓库不仅有 toy 数据，还有真实数据实验痕迹和产物，包括：

- `storage/public/routeA_phase1`
- `storage/public/routeA_phase2`
- `storage/public/routeA_phase2_cn`
- `storage/public/routeA_phase3_cn`
- `storage/public/routeA_phase4_disentangle_cn`

说明项目已经开始做真实跨文化场景下的原型验证，而不是只在合成数据上自洽。

### 3.3 已经有阶段性结果，不是没有方向

根据现有报告，可以明确看到：

- Phase 4 相比 Phase 2，推荐侧的 `serendipity` 有明显提升。
- 项目已经有 paired bootstrap 和 permutation test，不只是“看平均值”。
- 解纠缠侧也不是空白，已经支持 MIG / DCI / SAP 多 seed 评测。

换句话说，当前项目的状态不是“还不知道能不能做成”，而是：

> 核心机制已经做成了，下一步要解决的是证据质量、实验可信度和研究结论收敛问题。

## 4. 当前研究最关键的问题是什么

虽然项目已经有了较完整的研究原型，但当前最大的短板也非常清楚。

### 4.1 真实专家反馈不足

目前 PAL 流程虽然已经实现，但当前 Phase 3 里的 PAL 反馈仍然是**基于 metadata label agreement 的模拟反馈**，不是真正的人类专家标注。

这带来一个直接后果：

- 你可以说“PAL 机制实现了”
- 但你还不能强有力地说“真实专家反馈确实提升了模型”

这会直接限制论文主张的强度。

### 4.2 数据基准还不够稳固

当前已经有真实数据实验，但从论文级研究的角度看，仍然更接近：

- 小规模原型验证
- 多文化域初步实验
- 路线可行性证明

还不够像一个严格定义、可长期复用、可反复比较版本的“研究基准数据集”。

这会导致几个问题：

- 训练结果容易受数据清洗策略影响
- 实验版本之间不够容易横向比较
- 后续新增标注后，收益归因不够清晰

### 4.3 模型指标仍然存在明显权衡

当前结果说明模型不是“全面提升”，而是“某些指标提升，另一些指标未必同步改善”。

最典型的点在于：

- `serendipity` 提升明显
- 但 target culture 相关指标并没有表现出“已经很好地对准目标文化”

这意味着项目目前最需要的不是继续堆功能，而是让研究问题更聚焦：

> 模型到底要优先提升什么？
> 是惊喜度、文化校准、少数文化曝光、公平性，还是这几者之间的平衡？

### 4.4 目前还不适合直接宣称“大规模验证完成”

从当前代码与文档的边界来看，项目最适合的表述仍然是：

- runnable prototype
- proof-of-concept
- preliminary evidence

而不是：

- 已完成大规模公开基准验证
- 已实现 SOTA
- 已全面验证真实专家闭环

这不是坏事。  
这只是说明项目已经走完了第一段“把系统做出来”的阶段，现在进入第二段“把研究证据做扎实”的阶段。

## 5. 现在最该做什么

## 5.1 总体优先级判断

如果把接下来可能做的事情列出来，大概有这几类：

1. 继续改前端展示
2. 继续加新模型结构
3. 做大规模 backbone 微调
4. 收集真实音乐数据
5. 做专家标注
6. 做基于真实反馈的回灌训练
7. 做更系统的对比与评测

这几件事里，当前最值得优先投入的是：

1. 收集并整理真实音乐数据
2. 设计并执行专家标注
3. 用真实标注做回灌训练
4. 做统一评测比较

不应该优先做的事情是：

- 继续重心放在前端
- 先做大规模 backbone 微调
- 在没有真实标注闭环前继续频繁改模型结构

### 5.2 为什么不是先做 backbone 微调

原因很简单：

当前默认流程本身就还不是 full backbone fine-tuning，而是：

- foundation embedding extraction
- downstream DCAS training

在这个前提下，如果你现在直接做 backbone 微调，会有三个问题：

1. 变量太多  
   你很难判断收益到底来自更好的数据，还是来自 backbone 被改了。

2. 成本太高  
   算力、实验时间、参数空间都会显著上升。

3. 证据还不够值这个投入  
   现在真正缺的是“真实反馈是否能改善系统”，不是“模型容量还不够大”。

所以，backbone 微调不是不能做，而是**不应该作为当前第一优先级**。

### 5.3 为什么必须先做真实专家标注

因为当前 PAL 最大的问题不是机制没写出来，而是**信号来源不够真实**。

如果没有真实专家标注，PAL 相关结论会一直卡在一个尴尬的位置：

- 机制可运行
- 但研究说服力有限

而一旦你有了真实专家标注，你就能开始回答更有价值的问题：

- 哪类高不确定样本最值得标
- 哪种标注最能改善文化校准
- Pairwise constraints 是否真的有效
- Ontology 标注是否比普通标签更有帮助
- PAL 的单位标注成本带来多少收益

这才是后续论文和研究报告里真正有价值的内容。

## 6. 推荐的下一阶段研究路线

下面给出一个我认为最合理的执行顺序。

## 阶段 A：冻结当前基线

### 目标

在继续扩数据和标注之前，先把“当前最好的一版 baseline”固定下来，作为后续一切对比的参照物。

### 为什么要先做这个

如果不先冻结 baseline，后面每加一批数据、每加一次标注、每调一个超参，都会让你很难回答：

> 这次提升到底是因为什么？

### 具体要做什么

- 确认当前最重要的基线模型是哪一个
  - 大概率是 `routeA_phase4_disentangle_cn/model_tc_hsic.pt`
- 固化配套数据版本
  - `tracks.npz`
  - `interactions.csv`
  - `metadata_merged.csv`
- 固化当前最关键评测结果
  - 推荐指标
  - 解纠缠指标
  - 显著性检验结果
- 写一份 baseline 摘要

### 交付物建议

- `reports/baseline_phase4_frozen.md`
- `reports/baseline_phase4_frozen.json`

---

## 阶段 B：建立真实数据集 v1

### 目标

做一个真正适合后续专家标注与重复训练的数据集版本，而不是继续在零散数据上滚动实验。

### 为什么要做

因为专家标注是很贵的。  
如果数据集本身还不稳，专家标注就会浪费在后续可能被删除或重构的数据上。

### 数据集 v1 应该满足什么条件

至少满足以下要求：

- 3 到 4 个明确文化域
- 每个文化域有足够样本量
- 音频路径、元数据、标签字段可追溯
- CultureMERT embedding 可复现提取
- 训练/验证/测试切分固定
- 能与后续标注文件稳定对齐

### 推荐的文化域策略

不要一开始扩到太多文化域。  
建议先从当前已经有一定基础的数据域出发，例如：

- west
- india
- turkey
- china

原因：

- 你已经有 Phase 2 CN 路线
- 当前实验和报告对这几域已经有积累
- 能最大化复用已有脚本和结果

### 具体要做什么

1. 确认每个文化域的数据来源
2. 清洗音频与 metadata
3. 统一字段格式
4. 生成 `metadata_merged.csv`
5. 生成 `tracks.npz`
6. 生成 `interactions.csv` 或弱监督交互
7. 跑 dataset profile
8. 跑固定切分

### 交付物建议

- `storage/public/research_dataset_v1/`
- `reports/research_dataset_v1_profile.md`
- `reports/research_dataset_v1_splits/`

---

## 阶段 C：设计专家标注方案

### 目标

建立一套真正可执行、可训练、可评估的专家标注协议。

### 为什么不能直接“让专家随便标”

因为“专家标注”这四个字听起来很强，但如果没有结构，最后常常变成：

- 标了很多文本
- 很难转成训练信号
- 很难做统计
- 很难比较不同轮次的效果

所以，标注一定要服务于现有训练和评测框架。

### 当前最值得优先收集的标注类型

我建议按价值优先级排序：

#### 第一优先级：pairwise similar / dissimilar

形式：

- 给专家两首歌
- 问它们在某个维度上是否相似
- 要求给简短理由

为什么最优先：

- 能直接转换成现有 `constraints.jsonl`
- 最容易接入当前训练代码
- 最容易做回合比较

#### 第二优先级：ontology concept annotation

形式：

- 给一首歌标一个概念或多个概念
- 概念可以是文化情绪、演奏语境、风格语法等

为什么重要：

- 能扩展项目的“文化语义层”
- 能支撑后续 ontology 导出约束
- 对论文叙事也很有价值

#### 第三优先级：高不确定样本解释

形式：

- 对 PAL 挑出的高不确定样本，要求专家写“为什么难判断”

为什么重要：

- 它不仅能提供监督信号
- 还能帮助你发现模型真正困难的区域

### 当前不建议优先做的标注

- 大规模自由文本评论
- 完全开放式音乐学长文本
- 过细粒度但无法训练的说明

这些内容当然有价值，但在当前阶段性价比不高。

### 标注量怎么定

建议采用“小而强”的策略，而不是一开始大规模铺开。

一个务实的起步量可以是：

- 100 到 150 个高不确定样本
- 每个样本配 1 到 3 个对比样本
- 得到 300 到 600 条 pairwise 标注
- 同时补 100 到 200 条 ontology / concept 标注

这样做的优点：

- 成本可控
- 能很快闭环第一轮实验
- 足以判断真实标注是否比模拟反馈更有效

## 阶段 D：执行第一轮真实 PAL 标注

### 目标

把现在的“模拟 PAL”替换成“真实专家 PAL round 1”。

### 怎么做

1. 用当前最佳模型跑一轮 PAL uncertainty ranking
2. 从中选出最值得标的高不确定样本
3. 生成标注任务包
4. 组织专家标注
5. 整理为标准格式文件
6. 导出训练可用的约束文件

### 样本选择原则

不要纯随机抽。  
建议采用分层策略：

- 按文化域分层
- 按 uncertainty 分桶
- 覆盖容易混淆的跨文化对
- 优先选择模型最不稳定的边界样本

### 为什么要这样做

因为你要最大化单位标注成本的收益。  
专家时间应该花在“模型最需要人类判断”的地方，而不是花在显然正确的样本上。

---

## 阶段 E：基于真实标注回灌训练

### 目标

验证一个关键问题：

> 真实专家反馈是否真的能让模型比“模拟反馈”更强？

### 怎么做

建议训练三组模型：

1. baseline
   - 不加新专家标注

2. simulated-PAL
   - 沿用当前 metadata-based PAL 方式

3. real-PAL
   - 使用真实专家约束

### 为什么必须做这三个版本

因为这样才能真正回答：

- 真实标注比不标注强多少
- 真实标注比模拟反馈强多少
- PAL 的收益是不是来自机制本身，而不是来自数据噪声

### 训练时需要注意什么

- 先不要同时大量改模型结构
- 先维持和 baseline 接近的训练设置
- 保证比较尽可能公平
- 如果要调超参，也要在第二轮再做

这样你才能把第一轮结论聚焦在：

> 真实反馈有没有用

而不是被多个变量混淆。

---

## 阶段 F：做统一评测与结果归因

### 目标

把“模型好像变好了”变成“在哪些指标上、以多大幅度、在什么统计置信下变好了”。

### 重点看哪些指标

我建议按优先级看：

1. `serendipity`
2. `cultural_calibration_kl`
3. `target_culture_prob_mean`
4. `minority_exposure_at_k`
5. 解纠缠指标（MIG / DCI / SAP）

### 为什么不能只看 serendipity

因为当前项目的一个核心风险就是：

- 惊喜度上去了
- 但文化目标并没有真的更准确

如果只看一个指标，很容易把模型往错误方向推。

### 结果分析时要重点回答的问题

1. 真实专家标注是否带来稳定收益？
2. 收益主要体现在什么维度？
3. 是否存在文化域之间收益不平衡？
4. 哪类标注最有价值？
5. PAL 每轮的收益是否递减？

---

## 7. 现在不建议优先做什么

为了避免资源分散，下面这些事情当前不建议排到最前面。

### 7.1 不建议优先继续投入前端

原因：

- 当前研究瓶颈不在展示层
- 前端不会提升论文证据强度
- 当前最短板是数据与真实反馈

### 7.2 不建议优先做大规模 backbone 微调

原因：

- 成本高
- 干扰变量多
- 当前还没证明真实反馈闭环的收益

### 7.3 不建议继续频繁改模型结构

原因：

- 当前更缺的是稳定证据，不是新模块
- 如果结构和数据同时变，后续很难归因

### 7.4 不建议一开始铺很大规模专家标注

原因：

- 标注成本高
- 协议可能还没打磨好
- 第一轮应该先验证流程与收益，再决定是否扩量

## 8. 推荐的 4 周执行计划

## 第 1 周：冻结基线 + 整理数据集 v1

任务：

- 固化当前最佳模型与评测
- 整理真实数据源
- 统一 metadata
- 生成 `tracks.npz`
- 生成 dataset profile 和 splits

验收标准：

- 可以用一个固定命令从原始数据复现 dataset v1
- baseline 结果固定可复现

## 第 2 周：设计并试运行专家标注协议

任务：

- 明确标注字段
- 设计 pairwise 任务模板
- 设计 ontology 标注模板
- 从 PAL 中抽样生成第一批任务
- 小规模试标

验收标准：

- 能稳定产出训练可用的 `constraints.jsonl`
- 专家对标注协议没有明显歧义

## 第 3 周：真实 PAL round 1 + 回灌训练

任务：

- 完成第一轮真实标注
- 导出约束
- 用真实约束再训练
- 对比 baseline / simulated-PAL / real-PAL

验收标准：

- 至少有一轮真实反馈驱动的训练结果
- 所有对比结果能统一输出到报告

## 第 4 周：结果分析 + 决策下一步

任务：

- 做统一评测
- 看收益是否显著
- 看收益主要来自哪类标注
- 决定是否扩量标注
- 决定是否值得进入 backbone 微调阶段

验收标准：

- 有一份清晰结论说明“真实标注是否值得继续扩大投入”

## 9. 如果第一轮真实标注效果一般，怎么办

如果第一轮真实标注没有带来明显提升，不要第一反应就是“模型不行，立刻换大模型”。

应该先排查以下几个问题：

### 9.1 标注任务是否真的对应模型薄弱点

如果专家花时间标了很多“模型本来就会”的样本，收益自然有限。

### 9.2 约束格式是否损失了标注信息

专家可能提供了丰富解释，但训练时只用到了一个 `similar / dissimilar`，导致信息浪费。

### 9.3 标注维度是否太混杂

如果有的专家按情绪判断，有的按文化语法判断，有的按乐器音色判断，训练信号会变得混乱。

### 9.4 评测指标是否与标注目标一致

如果标注主要改善文化校准，而你只盯着惊喜度，就会低估标注价值。

只有排除这些问题之后，再考虑更大的模型升级，才是合理顺序。

## 10. 当前最重要的研究问题应该如何表述

如果要把下一阶段工作浓缩成一个清晰的研究目标，我建议这样表达：

> 在现有 DCAS 原型已经具备解纠缠、OT 推荐、PAL 与统一评测能力的基础上，下一阶段研究的核心任务是：  
> 构建一个可复现的真实跨文化数据与专家反馈闭环，验证真实人类标注是否能够稳定提升跨文化推荐中的文化校准、公平性与可解释性。

这个表述的好处是：

- 它承接了当前已有成果
- 它指出了当前真正缺的证据
- 它不会把项目重心带偏到无关方向

---

## 11. 最终建议

如果只给一个明确建议，那么就是：

**现在先不要把主要精力放在前端、backbone 微调或继续堆新模型结构上。**

**当前最值得投入的主线是：**

1. 固定 baseline
2. 整理真实跨文化数据集 v1
3. 设计真实专家标注协议
4. 跑第一轮真实 PAL
5. 回灌训练并统一评测
6. 再根据结果决定是否扩量标注或升级 backbone

简单说：

> 你现在最需要补的是“真实世界证据链”，不是“再加一个新模块”。

当这条证据链补起来之后，项目的研究说服力会明显上一个台阶，后面的模型升级也才更有方向。
