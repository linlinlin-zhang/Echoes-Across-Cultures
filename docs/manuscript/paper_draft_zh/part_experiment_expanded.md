## 4. 实验设置

### 4.1 数据集

**合成交互数据**：9,600条交互记录，240个用户，每用户40条交互，100%曲目覆盖率。

**源混淆度**：weighted\_source\_predictability\_from\_culture = 0.911765，表明文化标签能高度预测数据来源，这是一个严重的混杂因素。

**补充讲解（数据集为什么决定了论文上限）**：在机器学习实验里，数据集从来不是背景板，而是决定模型能学到什么、又会误学到什么的根本条件。如果某一文化几乎总是对应同一个来源，那么模型就有很大概率把“文化识别”偷换成“来源识别”。因此，这里不仅要报告文化和来源数量，还要报告它们之间是否高度绑定。这就是为什么 `weighted_source_predictability_from_culture` 这么重要，它在本质上是在量化“数据里有多少捷径可以走”。

合成交互数据也需要特别说明。它的优点是可控，可以精确控制用户数量、交互密度、覆盖率，从而更清楚地观察框架机制；缺点是与真实世界的日志行为仍有差距。真实用户会受平台界面、时间情境、社交传播和长期习惯影响，而合成交互更适合验证方法本身是否有潜力。

#### 4.1.2 routeA\_small 子集

routeA\_small 是一个高混淆度子集，用于测试框架在极端偏差场景下的鲁棒性：

- 640首曲目，4种文化，4个来源
- 96个用户，384个评估对
- 源混淆度 = 1.0（完美可预测）

**补充讲解（为什么要专门做一个高混淆子集）**：很多模型在“正常场景”下看起来都还不错，因为数据没有把问题逼到极端。但科学上更有说服力的做法，是专门构造一个足够苛刻的环境，去测试模型是否真在解决问题，而不是只是在利用巧合。`routeA_small` 就是这样一个压力测试场景。源混淆度达到1.0时，模型如果还能保持合理表现，才更能说明它具备真正的解耦能力。

### 4.2 骨干模型与训练配置

**骨干模型**：
- CultureMERT \cite{kanatas2025culturemert}：768维嵌入，针对跨文化音乐持续预训练
- Gemini：Google的多模态基础模型，用于对比实验

**训练配置**：
- 优化器：AdamW
- 学习率：0.002
- 批次大小：128
- 训练轮数：10
- 随机种子：42
- 正则化预热：3个epoch
- 成对约束：从epoch 2开始，预热2个epoch
- 排序约束：从epoch 4开始，预热2个epoch

**补充讲解（实验配置不是越复杂越好）**：一份好的实验配置通常追求的是“足够强但不过度堆叠”。比如 AdamW 是相对成熟、稳定的优化器；10 个 epoch 不算很长，但如果方法在较短训练周期内就能形成稳定优势，反而更说明它不是依赖超长训练硬磨出来的结果。预热策略的引入，则是在保护训练初期的稳定性，避免过多约束一上来就把潜空间压坏。

### 4.3 基线方法

我们在每个基准上评估了以下基线方法：

1. **popularity**：基于全局流行度的推荐，作为最简单的基线
2. **cosine**：基于预训练嵌入的余弦相似度推荐
3. **knn**：K近邻推荐，使用预训练嵌入空间中的距离
4. **lightfm\_like**：类似LightFM的混合推荐，结合内容和协同过滤
5. **bpr\_mf**：贝叶斯个性化排序矩阵分解 \cite{rendle2009bpr}
6. **bpr\_two\_stage\_hybrid**：两阶段BPR混合推荐
7. **bpr\_listwise\_hybrid**：Listwise BPR混合推荐 \cite{qu2025listwise}
8. **bpr\_lambdamart\_hybrid**：LambdaMART增强的BPR混合推荐 \cite{burges2010lambdamart}
9. **dcas\_full\_ot**：完整DCAS模型，仅OT检索，无重排序
10. **dcas\_full\_ot\_calibrated\_target**：DCAS目标校准操作点
11. **dcas\_full\_ot\_calibrated\_minor**：DCAS少数群体聚焦操作点

**补充讲解（基线为什么要有强有弱）**：实验里不能只拿一个很弱的对手来比较，否则提升缺乏说服力。这里保留 `popularity` 这类弱基线，是为了给读者一个最低参考线；保留 `cosine`、`knn` 这类直接利用预训练嵌入的方法，是为了检验“只靠强嵌入是否已经足够”；保留 BPR 和 LambdaMART 混合方法，则是在和成熟推荐范式做正面对比。只有这样，DCAS 的增益才有层次感，也更容易看出它到底赢在表示层、排序层还是公平性层。

### 4.4 指标与统计协议

**评估指标**：

- **惊喜度（Serendipity）**：度量推荐结果的意外性和有用性，计算为用户未交互但相关的推荐曲目比例
- **校准KL散度（Calib KL）**：度量推荐分布与用户历史偏好分布之间的KL散度 \cite{steck2018calibrated}，值越低表示校准越好
- **少数文化覆盖率（Minority@k）**：推荐列表Top-k中来自少数文化（曲目数 < 100）的曲目比例

**补充讲解（这三个指标分别回答什么问题）**：

- 惊喜度回答的是：“系统有没有推到用户原本不会主动找到、但其实值得喜欢的内容？”
- 校准 KL 回答的是：“推荐列表的整体分布有没有完全跑偏，还是仍然和用户历史兴趣保持某种一致？”
- Minority@k 回答的是：“少数文化内容在最终曝光里到底有没有被真正看见？”

这三者联合起来，才比较接近跨文化推荐真正关心的问题。如果只看 Recall 或 NDCG，系统很容易偏向主流热门内容；如果只看 Minority@k，又可能把列表做得过于理想主义而脱离用户接受度。

**统计协议**：

- Bootstrap置信区间：1000次重采样
- 排列检验：1000次随机排列
- Bonferroni校正：$\alpha = 0.05/10 = 0.005$（10次比较）
- 典型显著性水平：$p = 0.004975124$（1/201）

**补充讲解（这些统计术语怎么理解）**：

- **Bootstrap**：把已有样本反复“有放回抽样”，估计结果在重复实验中的波动范围。它特别适合样本量有限、但又想估计稳定性的情形。
- **置信区间**：不是“参数有95%概率落在这里”，更准确地说，它表示如果重复进行同类抽样过程，构造出的区间里会有大约95%覆盖真实值。
- **排列检验**：通过打乱标签或结果对应关系，构造“如果其实没效果，会看到什么差异”的零假设分布。
- **Bonferroni校正**：因为比较次数多了，就更容易“碰巧显著”，所以需要把显著性阈值调得更严格，减少假阳性。

如果要更口语一点理解，这些统计协议都是在防止研究者“看到提升就过早兴奋”。它们在问的其实是：这个提升到底稳不稳，还是只是随机波动刚好站在你这边。
